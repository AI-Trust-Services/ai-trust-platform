# ai-system-registry/ (port 8001, `/api/registry/`)
AI system registration and EU AI Act classification.
- `POST /api/v1/intake` — entry point for all registrations. Runs the classifier (< 10ms), assigns `SYS-XXXXXXXX`, persists to Postgres. The frontend never sends `tier` — classification is backend-only.
- `POST /api/v1/intake/batch` — batch import of already-classified systems from a JSON file (multipart, `file` + `target_status`). **Gated by `ENABLE_BATCH_IMPORT=true`** (default `false`; disabled in prod, enabled in dev/test via `.env` or the e2e conftest). Requires `systems:write`. Validates all records first, inserts valid ones in one transaction, reports failures. `target_status` (`approved`|`draft`, default `draft`) — tier-less records with `target_status=approved` are rejected as failures (not silently downgraded). Insert-only, no dedup — re-importing the same file creates duplicates by design. Max 1000 records / 10 MB per request. The four JSONB fields (`classification_rationale`, `field_confirmations`, `questionnaire_answers`, `registration_documents`) are never imported — always `NULL`. Response: `{imported: n, failed: [{index, name?, error}]}`. Payload format: `docs/batch-import-format.md`.
- `GET /api/v1/systems` — pagination `?limit=50&offset=0` (max 200).
- `POST /api/v1/systems/{id}/reclassify` — re-runs classifier, updates `tier`/`basis`/`annex_iii_area`.
- `classifier.py` — pure Python, no I/O. EU AI Act 4-tier waterfall, returns at first match (highest priority first):

  | Priority | Tier | Trigger |
  |---|---|---|
  | 1 | `prohibited` | Any Art. 5 flag |
  | 2 | `gpai-systemic` | `is_gpai` AND `training_compute_flops ≥ 10²⁵` |
  | 3 | `gpai-standard` | `is_gpai` AND `training_compute_flops < 10²⁵` |
  | 4 | `high` | Any Annex III flag |
  | 5 | `limited` | `is_chatbot` OR `generates_synthetic_content` |
  | 6 | `minimal` | none of the above |

  Logic is hardcoded (EU AI Act is law). Obligation texts/thresholds are constants in `classifier.py`.

**Dual risk label (high + transparency).** The waterfall returns a *single* tier, but EU AI Act Art. 50 transparency obligations *stack* on top of a high-risk classification — the **only** tier pair that co-applies (all other tiers are mutually exclusive; confirmed with compliance). A high-risk system that is also a chatbot / generates synthetic content matches `high` first and never reaches the `limited` branch, so the `limited` label is dropped from the stored `tier`. **Nothing stores a "second tier".** The data isn't lost: `is_chatbot` / `generates_synthetic_content` are raw boolean columns on the row (classifier *inputs*, not outputs), persisted regardless of tier. The frontend re-derives the stack at render time in `TierBadge` (`components/Badges.tsx`): when `tier === "high"` and either flag is set, it renders a companion "Transparency Obligations" badge. Scope is strictly high + transparency — do **not** widen to GPAI tiers without re-confirming with compliance. This is render-only; if a backend filter/report ever needs it, add a derived boolean to `AISystemResponse` and have the frontend read that instead of re-deriving.

**AI-assisted registration** — conversational alternative to the manual form. An LLM extracts descriptive fields and infers classifier flags; the **same deterministic `classifier.py`** produces the tier (the LLM never decides the tier). Stateless: the frontend holds the transcript + field state and resends each turn; nothing persists until `POST /v1/intake`.
- `POST /api/v1/intake/assist/turn` — one owner-flow turn. Body `{transcript[], fields{}}`; returns `{message, extracted_fields, next_field, complete, degraded, inferred_flags?, classification?}`. On `complete`, runs flag inference + `classify()`. Turn cap (`ASSIST_TURN_CAP`) → `degraded=true`.
- `POST /api/v1/intake/assist/extract` — multipart upload (TXT/MD/PDF/DOCX/PPTX/images), parsed via `documents.py` (max `ASSIST_MAX_TEXT_LENGTH`); images use `THALAMUS_VISION_MODEL`. Returns `{extracted_fields, notes}`.
- `POST /api/v1/intake/assist/engineer/{system_id}/turn` and `/extract` — engineer flow, same shapes, prompts focused on technical fields.
- `POST /api/v1/intake` accepts AI-collected fields, flags, and `classification_rationale` (JSONB `{flag, value, rationale, confidence}`); runs `classify()` when flags present. Manual owner mode sends no flags → stays a `pending` stub for the engineer.
- **LLM layer** (`app/llm/`) — Thalamus inference backend (OpenAI-compatible `/v1/chat/completions`). Stub mode when `THALAMUS_BASE_URL` is unset or `"stub"` (deterministic, offline, dev/CI); otherwise calls Thalamus with `THALAMUS_BEARER_TOKEN` as `Authorization: Bearer` (fails fast at startup if a real URL has no token). `THALAMUS_MODEL` / `THALAMUS_VISION_MODEL` select the served model IDs — switching is config-only. Malformed JSON → one auto-repair retry → `LLMParseError` → route returns 502, UI falls back to the manual form.
- **Externalized prompts** — prompt *wording* lives outside the code in repo-root `context/prompts/*.md` (one `.md` per model-call system prompt, named by a stable template id; see `context/prompts/README.md`). `app/llm/templates.py` resolves that dir (walks up to find `context/prompts`, or `PROMPTS_DIR` env override; baked into the image at `/app/context/prompts` via the Dockerfile) and exposes `render_template(id, **vars)`. Each `build_*` in `app/llm/prompts.py` renders its template and fills runtime vars (`target_schema`/`flag_schema`/`flag_names`); the JSON auto-repair call in `app/llm/parsing.py` renders `json_repair_system`/`json_repair_user` (var `malformed_response`). The field/flag data and message assembly stay in Python. A missing template or missing required variable raises `PromptTemplateError` with an actionable message; every render logs `prompt.rendered` with `template_id`+`template_path` for revision traceability (git provides the diff). **To change prompt wording, edit the `.md` — no code change.**
- All four assist routes gated `require_permission(SYSTEMS_WRITE)`.

**Side-effect-free evaluation** (`routers/classify.py`):
- `POST /v1/classify/evaluate` (`systems:read`) — runs the full LLM inference + deterministic classifier without writing to the database. Used by the document-indexing AI Test Bed to score sample fixtures. Body: `{answers: {business: {…}, technical: {…}}, enabled_sources?, injected_context?, prompt_override?, model?, role?}`. Returns `{tier, basis, obligations, confidence, rationale}`. Malformed LLM JSON → 502.
- `classifier.py` exposes `classify_from_questionnaire_answers(business_answers, technical_answers, injected_context="", prompt_override=None, model=None, role=None) → (ClassificationResult, rationale_dict)` — the reusable async core; `classify_ai_questionnaire(row)` is now a thin wrapper around it.
- **`role`** (`"engineer"` | `"compliance_officer"`) adds role-specific framing to the classification system prompt via the `{role_framing}` placeholder in `classify_questionnaire.md`. Engineers get flag-evidence/confidence emphasis; compliance officers get obligations/org_role/legal-exposure emphasis. When `prompt_override` is set it replaces the entire system message, so role framing does not apply. The framing text lives in `_ROLE_FRAMING` in `app/llm/prompts.py`.
- The `classify_questionnaire.md` prompt template accepts `{retrieved_context}` (context passages, or `""`) and `{role_framing}` (role-specific framing paragraph, or `""`). Both variables are always required; empty strings are valid.

**Registration modes** — `ai_systems.registration_mode` (`String(30)`, default `ai`) selects one of three intake paths:
- `ai` — conversational AI-assisted flow (above); LLM infers flags, `classifier.py` decides the tier.
- `manual_questionnaire` — structured owner + engineer questionnaire (below); flags come from boolean/number answer columns.
- `full_manual` — the compliance officer enters the tier directly (validated against `VALID_TIERS` in the router) and attaches supporting documents. No questionnaire sections.

An owner who registers with only name + purpose creates a **`pending`-tier** stub (`ck_ai_systems_tier` includes `pending` since migration `0017`); risk classification is completed later in Assessments. The **owner is the creator** — intake sets `business_owners` to the acting `x-forwarded-preferred-username`. Registration also captures `contributors` (JSONB list of usernames), `git_repo_url`, `planned_rollout_date` (DATE), and `deployment_country` (ISO 3166-1 alpha-2) — all nullable (migration `0039`). Migration `0039` also **dropped** `technical_owners`, `application_url`, and the EU-presence booleans `eu_output_usage`/`eu_market_placement` (no longer collected; EU AI Act is recommended unconditionally). Terminology-aligned lifecycle values (migration `0014_terminology_alignment`): `conformity`→`prod_ready`, `post-market`→`service`, plus new `updated`.

**Registration UI** (frontend) — the full-page `views/RegisterSystem.tsx` (route `/systems/new`) replaces the old register modal. Documents dropped on its upload panel go to the **document-indexing** service (`VITE_INDEXING_API_BASE`, `POST /systems/{id}/documents`, 50 MB, pdf/docx/md), not the registry's own MinIO endpoint; the first drop creates the system as a draft so uploads target a real id (abandoning the form deletes the draft, registering keeps it and lets uploads finish in the background). The systems table (`views/Systems.tsx`) shows Owner + Contributors + a per-system indexing percentage (indexed docs / total, polled from the indexing service) and disables **Go to Assessments** until indexing reaches 100%.

> **UI terminology: "Processing", not "Indexing".** All *user-facing* copy for document indexing says "Processing"/"Processed" (table column, tooltips, detail section/status). This is deliberate — "indexing" tested as not user-friendly. Keep internals ("indexing") as-is: variable names, API methods (`listIndexedDocuments`, `uploadDocumentIndexed`), the `document-indexing` service, and `VITE_INDEXING_API_BASE`. Don't "fix" the split — only visible strings were renamed. The upload-panel file-count ceiling (`MAX_FILES` in `RegisterSystem.tsx`) is 100 and intentionally not surfaced in the UI (anti-spam guard only; the real limit is the 50 MB/file size cap).

**Workflow endpoints** (`routers/workflow.py`, under `/v1/systems/{id}/workflow/…`) — after the single-page assessment redesign retired the section-based questionnaire/CO-review flow, only the flow-agnostic remainder survives:
- `GET /workflow` — step history (`SystemWorkflowStep` audit trail).
- `POST /workflow/assign` — record section assignees + intended purpose at assessment creation (used by the compliance "New Assessment" modal while the system is a draft; moves `draft → business_pending`).
- `POST /workflow/reset` — reset a system's `workflow_status` to `draft` when an in-progress assessment is deleted.
- Helpers `_get_steps` / `_active_sub_assignment` are imported by `systems.py` for its edit-lock logic. `ai_systems.workflow_status` ∈ `draft, business_pending, technical_pending, pending_review, info_requested, approved, rejected, returned` (CHECK `ck_ai_systems_workflow_status`); the new flow uses `pending_review` (= "locked"), `approved`, `returned`.
- **Retired (single-page redesign):** the section-fill endpoints (`submit-business`/`submit-technical`/`submit`/`submit-info`/`request-info`/`sub-*`), the per-question endpoints (`question-assign`/`question-answer`/`question-assignments`) + the `question_assignments` table (dropped, migration `0046`), and the CO-decision endpoints (`approve`/`reject`/`rce-summary`). Their behaviour now lives in `routers/assessment.py` (open/confirm/submit/issue/reject). `obligation_lookup.py` (hardcoded EU AI Act obligation titles/refs per tier+org_role) is retained.

**Single-page assessment flow** (`routers/assessment.py`, all under `/v1/systems/{id}/assessment/…`) — the redesigned owner-facing EU AI Act assessment (issues #346/#314 owner questionnaire, #347 submit/lock, #348 CO issue), **`ai` registration mode**. Replaced the section-modal questionnaire UX (the old `workflow.py` section chain + `question_assignments` are retired — see Workflow endpoints above). Per-question state lives in two per-system tables (migrations `0042`, `0043`):
- **`question_states`** (id `QST-`, unique `(system_id, question_key)`): `confirmed_at` (null = Incomplete) + `confirmed_by` (WHO confirmed — *owner-confirmed* = confirmed_by is the system owner, the submit gate; a contributor's confirm is progress only), `answer_source` (`ai_prefilled`|`manual`), `ai_original_answer` (to detect a change-from-AI), `confidence` (`high`|`medium`|`low`), and per-question assignment (`assignee_username`/`assigned_by_username`/`assigned_at`, null assignee ⇒ owner edits).
- **`question_comments`** (id `QCM-`): per-question thread, soft-deleted via `deleted_at`.
- Endpoints: `POST /open` (lazy, idempotent — one batched LLM **prefill** call proposes an answer + confidence per question from document-indexing retrieval, then the deterministic classifier derives the tier; seeds `question_states`), `GET /state` (start-page + sidebar view model: classification, confidence counts, `attention_count` = low-confidence-or-AI-unanswered, decisive questions, plus the read-only gates below), `POST /questions/{key}/answer` (autosave; a change from `ai_original_answer` flips `answer_source=manual` and reverts confirm), `POST /questions/{key}/confirm` (records `confirmed_by`; **422 if a changed answer has no comment** — mandatory-comment-on-change, server-enforced) / `/unconfirm`, `GET/POST/DELETE .../comments` (author or system-owner may delete), `POST/DELETE .../assign` (edit-gated, re-points `email_sender.notify_question_assigned`), `POST /finalize` (all-**owner-confirmed** gate), `POST /submit` (locks the assessment).
- **Read-only / locked (#347)**: `pending_review` *is* the "locked" state (no separate `locked` enum value). `GET /state` returns an assessment-level **`editable`** boolean (false when `workflow_status` ∈ {`pending_review`, `approved`}) + **`status_label`** (maps `pending_review`→`locked`, `returned`→`under_review`), and a per-question **`can_edit`** (`editable` AND the caller may edit that question — owner=all, contributor=assigned-only). When not editable, `answer`/`confirm`/`unconfirm`/`comment`/`assign` return **409**. `returned` (new value in both `ck_ai_systems_workflow_status` and `ck_assessments_status`, migration `0043`) is the CO-bounce target.
- **CO end view (#348)**: `POST /assessment/issue` (`systems:approve`) — final tier + `transparency` (combo rule: transparency only with `high`) + `confirmed` checkbox gate; sets `tier` + `co_issued_transparency` (migration `0045`), `workflow_status=approved` + `Assessment.status=approved` (atomic), immutable, notifies owner+contributors; 409 unless `pending_review`. `POST /assessment/reject` (`systems:approve`) — mandatory note → `workflow_status=returned` + `Assessment.status=returned`, reassign owner, notify; owner sees it as `under_review` and regains edit. `GET /state.transparency` = `tier==high AND (co_issued_transparency OR is_chatbot OR generates_synthetic_content)`; `TierBadge` renders the companion from it. Source docs (filename+page) persisted on `ai_systems.assessment_sources` at `/open`, surfaced assessment-level in the panel/modal.
- **`/submit`** requires every question **owner-confirmed**, then atomically (shared DB, one txn — like `advance-from-classification`) advances **both** `ai_systems.workflow_status` **and** the current compliance `Assessment.status` to `pending_review`, assigns the CO, and records an `assessment_submitted` step. (The lifecycle lives on the per-cycle compliance `Assessment.status`; `workflow_status` stays as coarse system state for the delete-guard + `TierBadge`.)
- **Prefill** (`context/prompts/assessment_prefill.md` + `build_assessment_prefill_messages`, task `assessment_prefill`) proposes answer *values* (not just the flags the classify prompt infers). Confidence bands are words only — **no numeric score anywhere** (by design). `app/assessment_catalogue.py` holds the backend question sections + the fired-flag → decisive-question mapping.
- **Frontend**: full-height app at `/systems/:id/assessment` (+ `/q/:questionKey`, `/submit`, `/issue`) under `views/assessment/` — `AssessmentApp` (loads/prefills, two sidebars), `AssessmentStartPage` (#346; shows a CO "Issue a Risk Classification" entry when locked + `systems:approve`), `QuestionView` (#314 — people-icon assignee dropdown + three-dot comment menu; disables inputs/Confirm/comment via `editable`+`can_edit`), `AssessmentSubmitPage` (#347), `CoIssueView` (#348). Sidebar has an "Overview → Assessment" back link + a per-question confirmation progress bar; completion keys off `owner_confirmed`; a contributor-confirmed question shows as an amber intermediate; when locked the Finalize button becomes a "Submitted — awaiting Compliance Officer review" banner. App header suppressed for these routes. Entry via `Systems.tsx`/`SystemDetailPage` + the compliance `/home/assessments` row-click redirect (`registry.openAssessment` handoff); the old `QuestionnaireView.tsx` + the compliance `QuestionnaireSection`/`RcePanel` are deleted.


**Other registry routes** (`routers/systems.py`):
- `PUT /systems/{id}` (`update_system`) — partial update. Uses `model_dump(exclude_unset=True)` (not `exclude_none`), so an explicit `null` is a *set* value and is distinguishable from an omitted field. Fields backed by NOT NULL columns (`_REQUIRED_FIELDS` = `name`, `lifecycle`, `org_role`) are rejected with **422** if explicitly nulled, rather than reaching `commit()` and raising a 500 IntegrityError. `tier`/`basis`/`annex_iii_area` are immutable here (use `/reclassify`). When `contributors` is present it is validated via `_assert_valid_contributors` (see below).
- `DELETE /systems/{id}` — permission is **not** a static `Depends`: the creator can delete their own system while `workflow_status == "draft"` with only `systems:write`; otherwise `systems:approve` is required. Once the workflow has started (non-draft), a non-approver gets 403 ("contact a compliance officer"). Permission is checked *before* the row is fetched so a 404 vs 403 can't be used to enumerate `SYS-*` IDs.
- **Contributor eligibility** (`_assert_valid_contributors`, called from both `intake` and `PUT`) — compliance officers (`ai_compliance_officer`) cannot be added as contributors (separation of duties: they *approve*, they don't contribute). The check calls the users backend (`USERS_BACKEND_URL` + `/users/by-role`); it is **fail-open** — skipped silently when `USERS_BACKEND_URL` is unset or the users service is unreachable, since the UI already enforces eligibility at selection time. Raises 422 on an ineligible username.
- `PATCH /systems/{id}/questionnaire` — merge-patch questionnaire answers (`section` = `business` | `technical`).
- `POST /systems/{id}/documents` — multipart upload of a supporting doc to MinIO, allowed for **any** registration mode (previously `full_manual`-only). Extension allowlist + `MAX_DOC_SIZE` 20 MB; filename sanitized/capped in `minio_client.object_key`. Metadata appended to `registration_documents` (JSONB). `GET /systems/{id}/documents/{index}/download-url` returns a presigned URL. **Note:** this is the registry's *own* MinIO path for manually-attached docs — distinct from the registration-form upload panel, which targets the separate **document-indexing** service (see "Registration UI").

**External read API** (`routers/external.py`, mounted at `/v1/external`) — a read-only surface for an **off-platform** consumer (e.g. an extracted AI Test Bed repo). Guarded by a static **bearer token**, NOT the platform's oauth2-proxy/OpenFGA model:
- `app/external_auth.py::require_external_token` — reads `EXTERNAL_API_TOKEN` **at call time** (so startup never depends on it); unset → **503** (feature off), wrong/missing `Authorization: Bearer <token>` → **401** (fail-closed, constant-time compare). FastAPI `HTTPBearer(auto_error=False)`. The bearer scheme is a deliberate seam — swap in OIDC/JWT later without changing the contract.
- `GET /external/systems` (`?limit&offset`) · `GET /external/systems/{id}` — AI system registration info (`ExternalSystemResponse`, read from Postgres; 404 on unknown id). **`ExternalSystemResponse` is an explicit allowlist** (defined in `routers/external.py`), **not** the internal `AISystemResponse`. Published: descriptive registration fields, `questionnaire_answers`, the EU AI Act classifier flags + headline `tier`, and `git_repo_url` (the data the off-platform Test Bed needs to read / re-run a classification). Withheld (internal operator state): assignee/owner usernames (PII), `registration_documents` (MinIO object keys), `field_confirmations`, `workflow_status`/`info_requested_section`/`registration_mode`, the `compliance` score, and the classification *detail* `basis`/`annex_iii_area`/`classification_rationale` (on `/assessment`). Adding an external field = a conscious edit to that schema, so new internal columns never silently publish.
- `GET /external/systems/{id}/assessment` — the system's EU AI Act **classification + justification**: `{ai_system_id, classification: {tier, basis, annex_iii_area}, justification}` (`justification` = the persisted `classification_rationale`). Read off the system row — **not** the compliance governance chain.
- `POST /external/systems/{id}/context` — **`search_ai_system_context`**: body `{query, k?, mode?, rrf_k?}` (mirrors document-indexing's `RetrieveRequest` minus `ai_system_id`, injected from the path); 404 on unknown id (same check as the other routes, before the downstream call); proxies `POST {INDEXING_BACKEND_URL}/v1/retrieve`, forwarding `x-forwarded-preferred-username: EXTERNAL_API_SERVICE_PRINCIPAL` (seeded `svc-external-api`, member of `auditor`) so document-indexing's `systems:read` check passes. Downstream 401/403 → 502 (principal mis-seeded), timeout → 504.
- **Env** — `EXTERNAL_API_TOKEN` (enables the feature), `EXTERNAL_API_SERVICE_PRINCIPAL` (default `svc-external-api`), `INDEXING_BACKEND_URL`. The token is surfaced read-only to admins in the Admin Settings UI (`admin` backend `GET /v1/external-api/token`). Exposure for a separate-cluster consumer is deferred (non-prod): reach it in-cluster or via `kubectl port-forward`; promote to a standalone service if it ever goes production.
- **Single-tenant only** — the bearer caller carries no tenant OIDC claim, so under `TENANCY_MODE=jwt` the tenant middleware (`libs/tenancy`) fail-closes every `/v1/external/*` request with 401 before the route runs (only `/health`/`/docs` are exempt). This is by design — the fix is **not** to exempt the static-bearer path from tenant resolution (that would bypass tenant isolation). Multi-tenant use would require mapping the external token to a tenant and propagating real tenant credentials to the downstream indexing call; out of scope.

**Langfuse tracing** (`app/langfuse_client.py`):
- `app/langfuse_client.py` — fail-soft wrapper around the `langfuse` SDK (same optional pattern as SMTP). `is_enabled()` is True only when `LANGFUSE_HOST` + `LANGFUSE_PUBLIC_KEY` + `LANGFUSE_SECRET_KEY` are all set; `get_langfuse()` returns a cached client or `None` (never raises). The Langfuse **project is fixed by the key pair**; per-deployment separation is by the Langfuse `environment` (`LANGFUSE_TRACING_ENVIRONMENT`, auto-set to the namespace/username by `k8s/scripts/bootstrap.sh` + CI).

## Frontend — Systems table (`frontend/src/views/Systems.tsx`)
The registry MFE's landing table (route `/systems`, issue #312). Columns: System Name, Owner / Created By, Risk Classification, Organisation Role, Registration Date, Actions. Patterns to know:
- **Cross-service assessment state** — the registry frontend now also consumes `VITE_COMPLIANCE_API_BASE`. `api.getAllAssessments()` does one broad `GET /api/compliance/v1/assessments?limit=500`; results are grouped client-side by `ai_system_id` to pick the row's single assessment menu item: no rows → "Start assessment" (sets the `compliance.pendingAssessment` localStorage handoff + Luigi-navigates to `/home/assessments`), rows but none `approved` → "Continue assessment", any `approved` → "View assessment". Continue/View only navigate to the (unfiltered) assessments list — they must **not** set the handoff flag (it only opens the create modal). The compliance call fails soft (`.catch(() => [])`): if compliance is down every system shows "Start assessment".
- **Hardcoded filter lists** — the Risk and Organisation Role multi-select filters use fixed option lists per the spec, **not** the backend enums: risk omits the GPAI tiers; org role includes `TBD`/`Product manufacturer` sentinels that match no real `org_role` (filter to nothing by design) and omits `both`. Badges still render every real tier/role. Filters are OR within a dropdown, AND across dropdowns.
- **Owner resolver (OPEN ITEM)** — there is no `created_by` column. The Owner column, Owner filter and owner search all route through `ownerKey`/`ownerLabel` in `Systems.tsx`, defaulting to `business_owners` (resolved to a full name via the `userMap` from `api.getAllUsers()`). The final field source is still undecided — change only those two helpers to switch it.
- Detail view is the existing `SystemDetail` Sheet overlay (name click + eye icon); delete uses a shadcn `Dialog` confirm. Build-time `VITE_COMPLIANCE_API_BASE` is wired in `frontend/Dockerfile`, `docker-bake.hcl` (`ai-system-registry-frontend` target), and `k8s/scripts/build-and-load-images.sh`.
